# Contributing to AliasDeck

Contributions are welcome. This file exists because AliasDeck enforces some
rules that are not obvious from reading the code, and having a pull request
bounced for a rule you had no way of knowing is a bad experience. Everything
below is checked by a test or a CI job — none of it is taste.

## Run what CI runs, before you push

```bash
make ci
```

That is `fmt-check`, `vet`, and the suite under the race detector. Two more
gates run in CI and are worth running locally when you touch what they cover:

```bash
make sqlc-diff        # after changing internal/store/sqlitestore/query.sql
go test ./internal/api/ -run OpenAPI    # after changing an API route
```

Two things that will confuse you if nobody warns you:

- `make sqlc-diff` compares against `git diff`, so it reports "drift" for any
  uncommitted change under `internal/store/sqlitestore` — including your own
  hand-written edits to `store.go` or a repo file. Check
  `git diff --name-only internal/store/sqlitestore` for a generated file
  before believing it.
- `ALIASDECK_REQUIRE_SHELLS=1` turns a missing shell from a skipped test into
  a failing one. That is deliberate: a skip reads as a pass, and the tests it
  governs are the ones proving AliasDeck does not write executable code into
  someone's shell. CI installs zsh and pwsh. If you do not have pwsh locally,
  run the suite without that variable and let CI cover it.

## The rules that will fail your PR

### The client and the server do not share code

Three tests in `internal/archtest` enforce this, and they fail the build, not
a lint:

- `TestClientBinaryNeverImportsServerPackages` — `cmd/aliasdeck` may not reach
  `internal/store`, `internal/api`, `internal/server`, `internal/sync`,
  `internal/web`, or `modernc.org/sqlite`, at any depth.
- `TestClientPackagesNeverImportServerPersistence` — same for
  `internal/source` and `internal/app`.
- `TestServerPackagesNeverImportRenderers` — the server may not import
  `internal/renderers`.

The last one surprises people. It means server code cannot reuse a helper
that lives in `internal/app`, because `internal/app` imports the renderers.
When both sides need the same knowledge, it belongs in `internal/domain`.
`domain.Alias.Miss` is there for exactly that reason: the CLI's `list` and the
server's device preview both need to explain why an alias does not apply, and
two implementations would be two sets of resolution bugs.

### The server never emits shell syntax

This is the project's core design decision, not a style preference. The server
transmits what an alias means; each client renders the syntax its own shell
needs. If a change would let the server influence the generated bytes,
`internal/verify`'s byte-identity test will fail — it renders the same aliases
through a local file and through the real HTTP server and compares the output.

### Generated files are generated

`internal/store/sqlitestore/*.sql.go` and `models.go` come from `query.sql`.
Edit the SQL, run `make sqlc-generate`, commit both. Hand-editing the
generated file passes review right up until CI regenerates it.

### There are two copies of the OpenAPI document

`docs/openapi.yaml` and `internal/api/openapi.yaml` must be byte-identical,
and the documented routes must match the registered ones exactly, in both
directions. Change an API route and you are changing three things.

### Every web route declares a guard

`internal/web` refuses to build its handler if a page declares neither
`guardPublic` nor `guardSession`. A route that is public by accident is the
bug this prevents.

### Both translation catalogues, always

`internal/web/i18n.go` holds English and Spanish, and
`TestCatalogsHaveExactParity` fails if a key exists in one and not the other.
Add every new string to both. Spanish here is neutral and professional, not
regional.

### No `<form>` inside a `<tr>`

An HTML parser hoists it out of the table and submission silently stops
working — and no Go handler test can see that, because handlers receive a
request body and never parse markup the way a browser does. The inline edit
rows gather their inputs with `hx-include="closest tr"` instead, and take the
CSRF token from the header `static/csrf.js` sets on every htmx request.

### Releases are bound to the client version

`internal/releasecheck` refuses to publish unless the tag equals
`"v" + app.Version` and the workflow's source ref equals that tag. Bumping
`internal/app/context.go` is part of cutting a release, not an afterthought.

## Tests

Behavior, not implementation. A test whose name states a property is worth
more than one that restates the code.

Two habits this project values:

- **Make the test fail on purpose once.** A regression test you have never
  seen fail is a test you are trusting on faith. Break the code, watch the
  message, put it back.
- **Say what breaks in the failure message.** `t.Fatalf("the edit dropped it")`
  tells the next person what went wrong. `t.Fatal("mismatch")` makes them read
  the test to find out.

## Commits and pull requests

Conventional commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`). Explain
*why* in the body — the diff already shows what. If a change encodes a
decision, the commit message is where it gets recorded.

Keep a pull request to one reviewable unit. If it is over ~400 lines, it
probably wants splitting.

## Disagreeing with the design

The architecture is still moving, so disagreement is useful. If you think a
decision in [`docs/PROJECT.md`](docs/PROJECT.md) is wrong, open an issue and
argue it. A wrong decision is cheapest to fix before people depend on it.

## Where to start

Issues labelled `good first issue` are scoped and have enough context to start
without asking. If nothing fits, open an issue describing what you want to
change before writing it — for anything larger than a fix, that conversation
saves both of us a rewrite.

# Why my alias server never sends shell code

I maintain a small tool that keeps shell aliases in sync across machines.
Partway through building it I made a decision that shaped everything after
it, and it is the part worth writing down.

## The obvious design is a remote dotfile

If you want `gs` to mean `git status` on every machine you use, the shortest
path is to keep the text somewhere central and have each machine fetch it:

```
alias gs='git status'
```

The server stores that line. The client downloads it. The shell sources it.
Done in an afternoon.

That design has a property I did not like once I looked straight at it: the
server is now typing into your shell. Whatever bytes it returns get evaluated
by your interpreter, on every machine, as you. A bug in the server, a
compromised host, a mistake in an admin's copy-paste — all of them become
code execution on every enrolled machine. The client has no way to tell a
legitimate alias from an injected command, because at that layer they are the
same thing: text to source.

Dotfiles in Git have the same shape, incidentally. The difference is that you
usually read your own commits.

## What I did instead

The server stores what an alias *means*, not how it is written:

```
name:        gs
command:     git status
platforms:   [macos, linux]
shells:      [zsh, bash]
```

There is no shell syntax anywhere in that. The client receives those fields
and produces the syntax itself, for the shell it is actually running. zsh and
bash get `alias gs='git status'`. PowerShell gets a function, because
PowerShell aliases cannot take arguments and pretending otherwise produces
something that looks right and behaves wrong.

The escaping happens on the client too, which matters more than it sounds. A
command containing a quote is escaped by the machine that knows which shell
will read it, not by a server guessing.

## Making it a boundary instead of a promise

A design decision that lives only in a document is a decision until the first
person is in a hurry. Two tests hold this one up.

The first forbids the client from importing server code at all. Not "should
not" — the build of the test fails if the dependency graph of the client
binary contains the store, the API, the server, the sync package, or the
SQLite driver. The client physically cannot grow a code path that talks to a
database, because the packages that could are not reachable from it.

The second is the one I like more. It resolves the same alias set twice —
once from a local YAML file with no server involved, once through the real
HTTP server — renders both, and compares the output. If those two paths ever
disagree by a single byte, the test fails.

That second test is what makes the claim checkable rather than rhetorical.
"The server does not send shell code" is easy to say. "The server cannot
influence the generated bytes, and here is the test that fails if it starts
to" is a different kind of statement.

It also bought something I did not plan for: the tool works with no server at
all. Point it at a local file and it behaves identically. The server is an
optional way to distribute the data, not the thing that makes the tool work.

## What it costs

Honesty requires the other column.

The server cannot ship anything the client does not already know how to
render. Adding a construct means shipping a client release, not a server
change. Every machine has to be updated before it can use it. That is slower
than editing a file on the server, and there are days it is annoying.

I think it is the correct trade. The set of things I want to send to every
machine I own is small, and it does not include arbitrary code.

## The general version

If you build anything that distributes configuration to machines, the
question is worth asking directly: does my payload get *interpreted* on the
other side, or *read*?

If it gets interpreted, your config channel is a code execution channel, and
it deserves the scrutiny you would give one. Sending data and rendering
locally is more work up front and much less to worry about afterwards.
